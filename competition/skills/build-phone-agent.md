# Competition builder: evidence to a regulated Freya workflow

Your job is to produce a phone-agent workflow from the run's supplied bank evidence and OpenAPI schema. You are the builder, not the phone agent. Do not contact Freya yourself. The host validates, saves, publishes, tests, exports and logs your artifact. Never read credentials, unrelated projects, personal settings or earlier runs.

Read every input document completely. Later explicitly scoped amendments replace earlier rules; record provenance and conflicts in `policy.json`. Extract all numeric limits, security fields and their order, calendar, bands, amounts, outcome/reason table, exception priority, transfer queues, callback windows, multi-product semantics, confirmation requirements and failure rules from these inputs. Do not assume they match the practice brief. Values from the brief belong only in generated run artifacts, never in shared builder code or this knowledge file. Tool names alone are stable; fields and enum values come from this run's OpenAPI. Do not silently reuse the base agent's incomplete policy. Reference customer identifiers, answers, balances and calendar examples are not runtime facts. Use call variables and actual bank responses.

Create `policy.json` with sources, extracted rules, unresolved conflicts and a compact machine-readable policy. Create `coverage.json` listing every substantive input rule and the node, condition, code or hook that implements it. No pretend coverage: mark omissions/uncertainty explicitly. Write `workflow.json`, a raw Freya workflow definition. An exported envelope is not an input definition. Do not emit agent_config or credentials.

## Platform pattern

Read the supplied workflow-format.md and tools-and-code.md. Follow their verified patterns. Base-agent.json is only a schema example. A lean reliable graph usually separates opening/security, account loading, deterministic account/calendar preparation, collection, and end. Use more nodes only when they provide a real gate. Avoid one code hop per trivial step; every hop costs latency.

Only identity and pre-identity closing/callback/human-transfer tools may exist before verification. Route to account loading exclusively on a real backend `all_verified` response (or the equivalent this API actually returns). Never extract `verified` from the customer's speech. Third parties cannot answer security questions. Do not place account objects or debt values in the initial prompts or test variables. Opening cannot identify the call as collection, debt or payment unless the supplied policy explicitly permits it. Use the requested dialogue language; do not copy the local demo's Turkish voice when the practice bank is English.

API bodies must match the supplied schema including enums and optionality. Fixed backend URL, method, headers and customer_id use `default`; model-filled answers/date/amount stay visible schema properties, without a default on a variable that has not yet been set. `maxRetries=0` on writing tools. Tool-level `response_mapping` belongs beside function/config; pre-action response_mapping belongs on the node. Paths start with `data.`. Booleans from the engine are strings; check true and True or map explicit string flags.

Use the documented `on_enter: {type: silent}` for API/code passthrough nodes. An empty TTS text is not a silent action: actual practice calls stopped immediately after a successful API response when an action node had an empty TTS entry. Preserve the final always fallback and result mappings so the next security question or permitted action actually runs.

Use code nodes to compute all business dates, deadline bands, floors and allowed callback days from `vars['now']` and the API's products. Read mapped arrays defensively as list, JSON string, or flattened keys; derive product_ids only from those records. Holidays and all parameters come from extracted policy. Give the dialogue a compact readable table of finished facts. Never use the host clock. Date phrases next/this weekday must obey the supplied definition; do not let a generic date extractor override it. Preserve vague/partial inputs until the customer completes or clarifies them. Corrections supersede earlier fragments. Ignore incidental dates in small talk.

Every structured event field consumed by state-machine code must be explicitly required in its extraction schema or have a faithful fallback from raw speech. Inspect the generated code's event.get keys against the actual extractor contract; a security event containing only kind/raw must not silently lose its answer. Provide one local contract round-trip for every event family, using minimal actual schema output rather than hand-populating hidden fields. Never rely on the dialogue model to fill gaps in authoritative bank state. For strict state-driven questions and statuses prefer a computed literal customer-facing sentence in the documented on_enter {type: tts, text: {{dialogue_line}}}. Each user reply can extract an event then route through deterministic code and re-enter the appropriate speech node. A tts string must contain the words to speak, not an imperative instruction. This prevents a freeform dialogue model from replacing a security question or claiming an unrecorded promise.

Each tool result needs an explicit actionable `what_to_do_next` sentence. After every tool result the phone agent must immediately speak or call its next permitted tool; it must never end a turn silently. Post-hooks receive an envelope, API body is result['data']. Hooks can write vars (observed in the kit). Strip headers. Keep flags strings, initialize every referenced state variable. Do not serialize the engine's copied full conversation or repeated code/debug strings as business state. Keep only the authoritative state, needed response facts and small extraction events; repeated metadata can overflow the sandbox output. Actual call traces remain in the engine separately and must remain reviewable.

Treat transport and sandbox execution failures separately from a valid bank response with ok:false. Inspect the documented automatic action failure counters/status fields before reusing a stored route; a failed post-hook can leave the old route unchanged. Avoid self-loops caused solely by that stale route. Provide a bounded, static failure exit that can speak and terminate even when code execution is unavailable; preserve successful writes already confirmed by the bank. Do not silently exceed retry rules. Keep acknowledgement and closing paths short enough for a customer waiting after confirmation; confirmed multi-product writes need factual speech when processing takes several steps, and the final bank close must actually occur before termination.

All snippets must compile, use only json/re/datetime, be wrapped in try/except with safe fallback values, and contain no double-curly template markers (including adjacent nested-dict braces). They run in the platform sandbox, not locally as builder tools.

Write routing and spoken control values through `vars` or assign explicit helper return values. Do not mutate `global route` or `global line` inside helpers: a local exec using one namespace can hide sandbox scope differences. A real practice trace advanced the product index but lost the helper's question/readback and spoke a generic missing-detail fallback. Preserve helper results explicitly and test the actual generated graph and API mappings, rather than only calling its business functions locally.

## Deterministic enforcement

Prefer actual code/hook guards to merely saying 'don't' in prompts. Gate get_account behind successful bank verification. Before create_promise, validate product_id, amount/floor/full, date/business/deadline, confirmed read-back for the exact current proposal and absence of a prior recorded promise for that product. Track attempt and retry limits in vars. A changed amount/date invalidates prior confirmation. Multi-product confirmation must cover the current set and each distinct date. Do not let a bare proposal count as confirmation. The dialogue can fill a boolean confirmation argument, but that alone is not a sufficient proof of a matching read-back: use node/extracted confirmation state and a stored pending proposal where practical. If a guard blocks an action, do not issue the bank write or fabricate ok:true. Fail closed using the verified platform mechanism; where stopping a hook is not verified, use a separate guarded code/API node or clearly state the enforcement limitation in coverage.

A customer can propose a valid date or amount and ask whether you are a robot in the same turn. Preserve the primary payment/security event and extract independent administrative-question flags; answer the question truthfully without dropping the proposal or fabricating an answer. Distinguish an offer from a required confirmation/read-back in the actual spoken wording; reading an already accepted floor back is not another persuasion attempt.

In the alternating-turn chat simulator, a silent non-passthrough conversation node cannot invite the next fragment reliably. Preserve the incomplete answer and counters, but provide a minimal continuation cue and ask only for the missing component. Never interpret an amount-only acceptance as acceptance of an unstated date. A complete payment non-answer must count under the input policy rather than leaving the initial ask unchanged indefinitely.

For persuasion, count only actual refusal/non-answers according to the brief, per product. An amount or date proposal is not a refusal. Do not repeat a refused offer. No persuasion on hardship unless the customer voluntarily offers payment. Transfers take precedence exactly as the policy says; preserve already recorded promises and prevent uncommitted writes. Do not describe unauthorized discounts, terms or plans.

For multi-product cases, implement the input's exact order, collective first ask, per-product bands/deadlines/floors/attempts, collective read-back, distinct create calls, required notes and outcome precedence. Notes must not be written before a transfer decision if the brief forbids any notes on transfer. Use atomic state for successful records versus pending agreements; a second failed promise does not erase earlier successes.

Extract amount scope explicitly for collective proposals: one total across products is not an amount for each product. A stated total equal to the sum of the relevant full balances plus a common date means those distinct full amounts, subject to each product's date rules. Otherwise ask for allocation; never copy the aggregate amount into every product or silently replace it with floors. Preserve completed product proposals while an unrelated product answer is unfinished. A partial correction invalidates confirmation but does not erase the previously accepted set, assign a new date, move the current product, consume refusal attempts, or commit anything. Negated dates such as "cannot pay today" must never become positive proposals through raw-speech fallback. Keep unfinished amount/date fragments separate from fully validated values and clear only the fragment actually superseded by a correction.

Before any note or write, require actual verified identity and the returned product record; privately known fixture IDs are not account provenance. A tool's name, HTTP method, URL and body schema must all bind to the same operation of the supplied API. Require nonempty coverage with explicit implementation status for every extracted substantive rule; empty, unknown or omitted coverage is not an implementation.

Each outcome comes from the supplied outcome table, not an invented code. Exactly one close_call must be last. For a state-machine agent, a fixed farewell line in on_enter tts and a passthrough transition into the dedicated close API, then a silent end_call, avoids an intent-based goodbye loop. The farewell string includes the actual final status and customer words, never a meta-instruction. Prefer a dedicated closing tool with a pre-hook that computes the outcome and notes from stored authoritative record state, a mapped string close_done, and a transition to a silent end_call node. The final goodbye must happen before close_call, not a model turn after it. Do not use both lifecycle close_call and model-visible close_call. On promise API failure, retry only within policy; never tell the customer a promise or transfer was recorded without ok:true. Never set a success flag from HTTP success alone when data.ok is false.

When a later repair phase provides official case failures/transcripts, diagnose the actual root cause: mapping, routing, code exception, missing policy, honesty, or latency. Fix only the generated files in this run. Do not tune to known customer identities, exact expected records, or fixed dates from the test set. Maintain general behavior from the bank evidence. API dry-run rejection is feedback too. Make the smallest coherent correction and regenerate coverage.

## Output contract

Write only within the current run workdir. You may use shell/Python to generate and locally inspect JSON and snippets. Do not install packages, call network services, start other agents, modify kit files, inspect auth files or submit anything. The host owns Freya calls and official scoring. Finish with the required structured artifact paths and a brief honest summary. This is a real build; placeholder workflow graphs or hardcoded call transcripts are unacceptable.

A mandatory guard that cannot execute must fail closed. Never add an LLM collection/write fallback in an outage to improve a practice score. Explicitly degraded enforcement is rejected by the host; preserve static safe exits and honest error states.
