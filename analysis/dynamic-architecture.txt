ARCHITECTURE COMPARISON
architecture: Sentence decision tree / expanded DAG
state_representation: One branch per utterance or path; revisits require duplication.
diversity: Poor if phrases are hard-coded; free-language nodes can still be diverse.
safety: Auditable on short paths, brittle under corrections and interruptions.
growth: Branching b over depth d can yield O(b^d) path expansion.
freya_fit: Valid subset, unnecessarily restrictive.
decision: Reject as the organizing abstraction.

architecture: Fixed flat FSM with data
state_representation: Finite phases plus explicit slots.
diversity: Not inherently restricted: a state can have an open semantic prompt.
safety: Good coarse identity gating; state explosion if all product/interrupt combinations become states.
growth: Cartesian combinations remain large if flattened; symbolic variables can avoid enumeration.
freya_fit: Directly supported by nodes, variables and transitions.
decision: Use for external-effect boundaries, not sentence choice.

architecture: Hierarchical FSM / statechart
state_representation: Orthogonal identity, dialogue, product and terminal state; resume focus is data.
diversity: Local dialogue freedom and reusable interrupts.
safety: Shared predicates avoid duplicated fragile edges; precedence must be explicit.
growth: Compact representation; formal exploration can still be exponential.
freya_fit: Lower to flat nodes + vars. Native nesting, deep history and parallel regions unconfirmed.
decision: Use as the policy design model.

architecture: Constrained planner / receding horizon
state_representation: Enabled actions and outstanding obligations, re-evaluated after each user or tool event.
diversity: Handles novel combinations and clarifications without prewriting every path.
safety: A planner proposes; sound guards authorize. Semantic extraction remains fallible.
growth: Bound candidates and planning depth; do not run MCTS/full search per spoken turn.
freya_fit: Prompt-level action choice supported; arbitrary planner runtime/network framework unsupported.
decision: Use a one-step chooser over legal skills, not autonomous long tool sequences.

architecture: Skill graph with guarded contracts
state_representation: Reusable ask/clarify/explain/verify/negotiate/readback/record/transfer/finalize skills with preconditions and results.
diversity: Wording and legal ordering can adapt; schema and authorization do not.
safety: Capabilities need state/revision/product/argument binding; seven tools is not seven permanent permissions.
growth: Approximately O(rules + skills + endpoints) graph and O(products) data for this brief; no claim that all planning is polynomial.
freya_fit: Compile into documented conversation/code/api_request/end_call nodes.
decision: Recommended combination with hierarchical policy state.

THE DESIGN
compiler_separation:
  policy_ir: Compile source clauses and explicit B-over-A replacements into typed predicates, parameters, obligations, priorities and operation schemas. Preserve provenance. LLM source extraction is a fallible front end; reject unresolved conflicts and unsupported mechanisms before export.
  extraction: Produce user assertions only: identity-answer text, customer/third-party status, questions, date expression, amount expression, product reference, correction/withdrawal, clear assent, and requested support/human/restructuring. Never extract trusted verified, recorded, customer_id, approved_date, closed or backend_ok from speech. Separate namespaces ex_* / st_* / dispatch_* / result_*.
  ambiguity: Do not collapse a mixed utterance to one intent enum: 'yes, but change the loan date' contains correction plus assent. Capture independent flags/raw spans, then prioritize corrections and policy-specific interrupts. Require an evidence turn and the current readback revision for assent. Confidence thresholds are not authorization.
  freshness: Reset ephemeral extraction fields to an explicit unset sentinel after consumption, with a consumed event revision. Do not interpret a still-set variable as fresh confirmation. Node current_turns resets on transitions; use an explicit call-wide count or documented total_turns, not it as a durable event ID.
  routing: On every new user turn route to the reducer before dialogue or an external action. The reducer computes one string route_target from validated state. Emit grouped OR comparisons, nested AND only where necessary. Do not hide mandatory interrupts behind an always edge or loop_condition.
  dialogue: Render a compact view: verified-safe facts, active product, remaining obligations, currently permitted speech acts, required literal lines and the next question. The model may paraphrase, answer supported questions and acknowledge emotion. It cannot announce speculative success or add financial terms.
  dates: Preserve raw relative-date wording even if using type=date. The default extractor anchors to system today and concretizes vague periods, while A uses supplied now and sometimes requires clarification. Override with the documented extraction placeholders plus the injected anchor, then deterministically re-resolve and validate from raw expression. Never trust extraction's guessed date as a commit date.
  tool_results: Normalize envelopes and true/True explicitly into string status flags; never use bool('false'). Match each result to an outstanding dispatch. Build next-action instructions from trusted status/policy, not arbitrary text in the tool payload.
  coverage: Map every clause to the actual extractor/routing guard/dialogue obligation/commit check/test that implements it. A source-ID row without an enforcement site is inadequate.
state_and_events:
  policy: policy_version and source-derived calendars, amounts, bands, retry limits, identity order, queue/outcome/reason maps; immutable for a call.
  runtimeclock: RuntimeClock(now_iso, local_calendar_basis, source='call_variables.now') is an explicit adapter concept, not an existing class. Freeze injected now for the call. Missing/invalid now blocks date-dependent operations rather than falling back to wall time. Do not infer Europe/Istanbul from this workstation for a bank brief that supplies a naive local datetime. Physical latency uses a separate monotonic timer.
  trusted_state: Identity stages and counters from successful normalized verification results; ordered account products from get_account; product-specific deadlines/floors; outstanding questions; refusal, hardship and vague-date counts; current readback revision; pending terminal reason; pending action; speech obligations.
  product_state: Each product has proposed terms, confirmed terms bound to a batch revision, recorded terms and backend receipt, persuasion count, create attempt count, disposition candidate, note acknowledgement. A recorded promise is immutable; later failure on another product cannot undo it.
  event_schema:
    event_id: monotonic local sequence
    kind: user_observed | extraction_candidate | correction_received | readback_emitted | confirmation_received | dispatch_reserved | backend_result | note_buffered | finalize_requested | input_closed | close_acknowledged
    origin: user | extractor | kernel | transport | emitted_transcript
    turn_revision: integer
    action_id: optional integer from kernel, never model-selected
    payload: typed, schema-checked data
    source_ids: policy clauses applied
  reduction: state_next = reduce(state, event, immutable_policy). Accepted user facts and actual tool receipts are distinct from proposed commands. Preserve a compact trace in vars as explicit JSON; state summaries are projections, not evidence replacing receipts. Do not store unnecessary raw security answers in summaries.
  confirmation: Any real user correction or withdrawal invalidates the outstanding batch immediately, including an out-of-policy replacement. Validation failure must not resurrect old assent. An invalid internal planner candidate is a different event and need not revoke assent. A bare yes is valid only in direct response to the current complete readback, with no correction or overriding request in that turn.
  partial_commit: For B, one batch readback and confirmation authorize serial create_promise calls in account order. Re-evaluate queued user events between writes. Successful products stay recorded; definitive double failures become buffered service_error; transfer discards only unrecorded proposals/confirmations and buffered notes.
  state_size: Per-product records and an active index replace product-specific graph copies. The representational improvement is linear in product count for these fields; reachable combinations and verification remain potentially exponential.

planning_and_adaptation:
  allowed: The dialogue can choose how to clarify, which supported question to answer, whether a user utterance changes the pending task, and which enabled skill serves the next obligation. Choose one next action, execute at most one effect, then recompute from the observation. Strict product order and persuasion rules still constrain choice.
  forbidden: The live model cannot add tools, edit policy predicates or constants, reinterpret its own tool success, rewrite ledger history, train weights, run arbitrary Python, or authorize itself.
  skill_contract: Each reusable skill carries id, preconditions, read/write set, allowed speech facts, required speech, postconditions, interruption rule, budget and source IDs. Skills are internal compiled operations, not newly exposed bank endpoints.
  model_selection: README fixes the phone-agent model to AGENT_LLM. Builder models may differ; the researcher request does not authorize changing deployed phone models. Simulation overrides must match the event rules. reasoning_override exists but only works for supporting models; it is not a verified adaptive-model facility.
  adaptation_scope: Adapt prompts, semantic focus and action proposals inside the fixed kernel. At build time an independent critic may propose a bounded repair from source-linked counterexamples, followed by held-out and mutation checks. No live learning or permission expansion from customer text.
  latency: Do not add multi-agent debate, MCTS, SMT compilation or repeated critic models to each voice turn. Reuse Freya's existing extraction/routing/dialogue path and small code reducers. Bound planner retries and global tool/turn loops; preserve source counts and flag a noncompliant timeout outcome instead of inventing one.
  unknown_scenarios: A new phrasing or combination can map to existing facts and skills. A genuinely absent bank operation is unavailable; A44 requires an honest information limit. Novelty does not grant authority.

LOWERING TO DOCUMENTED FREYA NODES
baseline: Use ordinary cyclic nodes; no new server, framework import, custom handler or endpoint. Keep bank APIs out of free-dialogue tool arrays in the smallest strict variant. Capabilities are code-authorized reachability to seven fixed dispatch nodes, not 2^7 copies of tool subsets.
logical_nodes:
  name: init_state
  type: code
  purpose: Initialize every state/sentinel, policy version, injected clock, counters and route target. Verify mandatory call variables without printing customer_id.
  name: opening / identity_dialogue
  type: conversation
  purpose: Required first disclosure and who-is-speaking question; collect only user assertions. No account tools. Every user event goes through reduce_user.
  name: security_dialogue
  type: conversation
  purpose: One current security question and corrections/questions; sensitive data unavailable. Routing depends on reduce_user and actual verify results.
  name: service_dialogue
  type: conversation
  purpose: All-products disclosure once, negotiation, questions, hardship and selected safe skills. One reusable node, active product stored in data. No arbitrary external calls.
  name: readback
  type: conversation
  purpose: Render the exact ordered batch product/amount/date facts, ask for confirmation and wait for a user turn. Entering the node alone is not proof a complete line was delivered.
  name: reduce_user
  type: code
  purpose: Consume fresh extraction fields; process questions plus corrections plus interrupts; invalidate assent when needed; calculate allowed action/arguments and dialogue view; route once.
  name: dispatch_verify / dispatch_account / dispatch_promise / dispatch_callback / dispatch_transfer / dispatch_note
  type: api_request
  purpose: One fixed endpoint per bank operation, fully baked args from guarded dispatch_* variables. No model-supplied customer_id/product/status fields. maxRetries=0 for writes; preferably connect_retries=0 for deterministic attempt accounting.
  name: reduce_result
  type: code
  purpose: Normalize the actual response, consume one matching pending action, keep per-product partial commits, refresh all dispatch fields and speech obligations before returning to dialogue or the next warranted action.
  name: goodbye / finalize_gate
  type: conversation then code
  purpose: Say goodbye before close. Finalize only when the last admitted user event is reduced. Freeze terminal branch and flush B notes only if the real input boundary probe passes.
  name: dispatch_close -> end
  type: api_request -> end_call
  purpose: Dispatch close_call once with reduced outcome/reason; route on normalized result to platform hangup without another bank call. Post-hook may record acknowledgement; no bank effect after close.
scheduling: conversation receives user -> extraction -> always transition to reduce_user -> deterministic route -> conversation on_enter speaks and waits, OR guarded API node runs -> reduce_result -> next conversation/action. Never make the dialogue node passthrough during ordinary conversation. Avoid unconditional passthrough cycles. User and tool events must have distinct consumption markers so reduce_result cannot accidentally reconfirm a previous yes.
state_transport: Serialize JSON-safe state and events explicitly through vars; object identity of Python BackendAttempt cannot survive separate sandbox invocations. Replace identity checks in the emitter with a kernel-owned action_id, expected operation, bound arguments, policy/state revision and dispatch status. This is logical integrity within trusted code, not a cryptographic token.
baking: All required dispatch fields are set before entering api_request, ensuring default binding sees validated values. Do not rely on changing vars after tool registration to refresh baked arguments. A stale default can silently replace a new model value. Clear previous result/status fields before dispatch; never reuse a success from the previous product.
sandbox: Only json/re/datetime imports are verified. Do not import policy_runtime.py, dataclasses, Decimal, Z3 or LangGraph into Freya by assumption. Generate small equivalent JSON-state code using verified modules; differential-test against the local Python oracle. Avoid adjacent double braces anywhere in snippets; initialize safe fallback values and catch exceptions to deny dispatch.
money: Local oracle uses Decimal; target emission can compare canonical decimal strings or scaled integers losslessly. Decimal import is unconfirmed. Neither the brief nor OpenAPI supplies a cent quantum: do not silently add quantum=0.01 as policy. Bind a quantum only when a source states one; otherwise preserve exact admissible decimals and reject malformed/nonfinite values. Test wire numeric serialization separately.
result_instruction: Return trusted next-action facts via rendered dialogue view or a code-authored post-hook message. Strip irrelevant headers. An API payload's arbitrary 'what_to_do_next' text must not become authority.
turn_budget: Track total conversation user events and non-speaking internal steps explicitly. Freya current_turns resets on reentry; max_node_turns without max_turn_transition does not terminate. Budgets prevent accidental loops but cannot invent a source-approved closing reason.
deployment_validation: Parent must save/export/read back the workflow and compare retained fields, then run the official fixed models. This task does not call Freya.

WHOLE-CONVERSATION OBLIGATIONS AND FAILURE SEMANTICS
note_barrier: B10 is a whole-trace property: transfer_exists => no add_note anywhere. Buffer dispositions, do not call add_note while the conversation can still select transfer. An internal finalize_non_transfer lock only prevents transfer execution; it does not prove compliance if the caller can still insist on a human. A valid barrier requires that all previously admitted user events are processed and no new policy-relevant input can be admitted before notes/close complete.
impossibility: For any open prefix ending just after an irreversible note, an allowed future user continuation can demand transfer. With no undo endpoint, an online controller cannot both honor that continuation and erase the prior note. This is an architectural inference, not a Freya observed failure. Either an actual input cutoff makes the conversation finite, or the platform/brief must resolve the conflict. A longer FSM or a smarter model cannot remove it.
concrete_terminal_sequence: Drain admitted user events -> resolve transfer priority -> emit required final speech/goodbye -> establish real input closure -> freeze terminal choice -> B non-transfer: add_note acknowledgements in order -> close_call once -> end_call. If the platform admits a user turn before closure, abort tentative finalization and re-reduce it; nothing irreversible should have been flushed yet.
lifecycle_caution: end_of_call tools run after call analysis and before judging; response_mapping is not applied then. The docs do not establish ordered multi-call transactional flushing. Do not substitute an end-of-call LLM summary for explicit bank outcome state.
attempts: Use policy attempts per product, not total transport-success counters. A create_promise HTTP 500 is explicitly definite no-write in this mock, so A37 allows one repeat. An HTTP 200 ok=false likewise means no action was carried out. Timeout/disconnect after dispatch is unknown, not definite failure.
unknown_result: Keep the outstanding attempt pending, prevent a second write, and retain a pending user interrupt. A late response matching that attempt may settle it, then the interrupt wins before further writes. With no late response or reconciliation endpoint, the call is observably incomplete; never fabricate service_error, recorded or transferred as success.
partial_commits: Success on p1 followed by two definite failures on p2 retains p1, marks p2 service_error, continues eligible p3, and records only missing-product notes at a valid non-transfer boundary. Transfer after p1 preserves p1 and abandons every unrecorded promise and note candidate.
close_error: Current begin_close reserves a terminal send, not a receipt. Track close_dispatched/close_acknowledged/close_unknown explicitly. A46's exactly-one close call and OpenAPI's repeatable-500 description have an unresolved edge if close itself fails: do not silently use generic automatic retries and claim both requirements. A successful complete fixture has exactly one close dispatch; failure is a failed evaluation, not a fabricated alternate outcome.
priority: Contextual source priority beats generic route priority: hardship handling precedes persuasion/restructuring when applicable, proposed date/amount is not refusal, and an actual transfer dominates a previous promise at close. An open question and a correction can coexist in one user turn.
